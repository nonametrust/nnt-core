# M3, the synchronous path and the brief: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Design authority:** the board card "M3 · Senkron yol ve brief" on
> `github.com/orgs/nonametrust/projects/1`, and §6 of
> `docs/superpowers/specs/2026-09-05-mvp-v0-core-engine-design.md`. This plan was
> written against the SHIPPED CODE rather than against either, which is the rule
> that has now paid four times: M2's plan read against M1's code found two
> contradictions, the storage card's plan found the four its card knew about and
> seven it did not, and the survey behind this plan found that the storage card's
> own §2d had handed M3 a finding that was backwards. Section 1 is what the rule
> produced this time.

**Goal:** the engine's synchronous path. An observation arrives, is folded into
a baseline, is tagged by M2's arithmetic and written by the store as handed; and
a `brief` over the stores returns a graded answer with its reasons and their
sources, with an active tag lowering that counterparty's threshold, and with a
named behaviour per risk tier when a store cannot be reached. At the end of M3
the two verbs the whitepaper promises, `observe` and `brief`, both exist.

**Architecture:** one new package, `packages/engine`, which is the first module
allowed to import BOTH `@nonametrust/store` and `@nonametrust/tagging` — it is
the composition point those two packages were kept apart for. One new versioned
value `BriefPolicy` lives there. One new migration, `0008`, for the one thing
relatedness cannot be computed without. The brief is a pure function: it takes
its instant, its ids and its policy as inputs and returns a value plus a list of
effects, and a thin wrapper performs the effects. Everything invariant stays held
by Postgres; the TypeScript refuses first and names the class.

**Authorities read:** the M3 board card and its 27 September addendum; `docs/superpowers/ledgers/2026-09-12-m2-decisions.md` §"Carried into M3 and the schema card" (615-743); `docs/superpowers/ledgers/2026-09-26-storage-card-decisions.md`; `docs/superpowers/plans/2026-09-21-storage-card.md` §2b (R9-R21), §2c (the limits of crypto-shredding), §2d (what later task texts get wrong AND the eight findings left unfixed); the M1 ledger; the core-engine design §1, §2, §6-§9; every file in `packages/store/src` and `packages/tagging/src`; migrations `0001`-`0007`.

## 1. Findings: where the shipped code contradicts the design, or the design contradicts itself

Each of these was measured against code, with file and line. They are the reason
this plan makes twenty-one rulings before a task starts.

**F1. "A pure function over the stores" and "note the trigger" cannot both be
true.** Design §6:259-268 says the brief is pure and that its flow includes
noting the trigger. Noting a trigger is `TriggerEventRepository.record`
(`store/src/repositories/trigger-event.ts:52`), a write, and its row needs an
`observationId` under a foreign key (`0006:85-87`), so the intent must already
exist as an observation — and `append` refuses a `Transaction`
(`store/src/repositories/observation.ts:153`, R21), as does `AuditChain.append` (`store/src/audit/chain.ts:269`). M1's
own story pins that a brief leaves the tag table byte-for-byte untouched
(`store/src/acceptance.test.ts:411`). So three writes hang off one "pure
function" and two of them cannot share a transaction with anything. Cost of
building on the design's sentence: three wrappers each invent their own write
ordering, and a retried brief records the same trigger twice.

**F2. There is no brief threshold anywhere in the code, and the one threshold
that exists is a different quantity.** Design §6:275-277 says an active tag
lowers that counterparty's brief threshold and that the engine exposes the
current threshold as a query; §8:330-334 says both numbers live in a versioned
policy file. `Policy` (`tagging/src/policy.ts:22-82`) carries no brief
threshold, no active-tag factor and no relatedness floor. The only threshold in
the tree is `tagThreshold` (`tagging/src/threshold.ts:77`), θ_tag in robust-z
units, applied per reading at ingest, stored nowhere, not per counterparty, and
lowered by nothing. The design's vocabulary has three thresholds and the code
has one.

**F3. The brief's "sources" requirement collides with retention by
construction.** Design §6:270-273 says each reason carries its sources. A tag
names only its opening observation — `observation_id` is identity, frozen by the
guard (`0007:212-220`) — and `refresh` writes only `g0`, `tagged_at`,
`refresh_count` and `saturation_state` (`store/src/repositories/tag.ts:233-238`),
so a tag refreshed forty times names one observation and the store records the
other thirty-nine nowhere. Worse: `source.ref` is inside the sealed payload
(`store/src/repositories/observation.ts:228`), so once the month key is
shredded the reason has no source.

**Measured, because the first draft of this finding asserted the interval and
got it wrong.** The grace runs from the close of the INGESTION month, not from
the observation: `periodOf(ingestedAt)` at `observation.ts:221`, and
`expiresAt = periodCloses(period) + graceDays × DAY` at `retention.ts:212-213`
with `graceDays: 90`. So two observations ingested in the same month expire at
the same instant, and the window is **90 to 120 days after ingest** rather than
"roughly four months": one ingested 30 September expires 90.04 days later, one
ingested 1 September 119.6 days later. Both measured on a probe, with the sweep
one millisecond early returning nothing and the sweep at expiry shredding the
period and turning both `get` calls into `PayloadExpired`.

The half-life plays no part in that arithmetic, and an earlier draft wove it in
as though it did. What it says is something narrower: an unrefreshed tag in that
state holds under one per cent of its `g0` at the 14-day half-life
(`calibration.ts:116`) — 0.0070 and 0.0016 for the two probes. A tag refreshed
yesterday is at full strength and still names a source that will not open.

And `listLive` has no shred gate: after the sweep it returns both tags with
`retiredAt: null`, and after `shred(ns)` it still returns them while every
source read raises `NamespaceShredded`. Measured.

**F4. Relatedness cannot be computed today, and the missing half is a data
model.** Nothing in any `src` computes it. Aspect matching has its inputs: the
tag row carries `channel` and `aspect` (`0007:143`) and the intent's reading
comes from `readObservation` (`tagging/src/reading.ts:138`). The entity graph
does not: a continuity assertion — the thing that links a wallet to the endpoint
whose payment address it is — is provenance INSIDE the sealed payload
(`schema/src/namespace.ts:54`), the `namespace` table holds `kind`, `ns_id`, the key, its shred instant and
`created_at`, and no edge (`0001:26-35`), and no table links two namespaces. M1's
own story links WALLET to PROVIDER only inside one observation's payload
(`store/src/acceptance.test.ts:123-139`) — unreachable without decrypting and
unreadable once that month expires. So relatedness today is at most (same
namespace) × (channel/aspect agreement).

**F5. "The condition is logged" has nowhere to go when the store is
unreachable, and the `tier` column cannot hold the risk tier.** The only log
this system has is the audit chain, in the same Postgres as every store
(`db.ts:105`). A connection failure carries a driver errno and not a SQLSTATE — measured,
`ECONNREFUSED` — so `mapPgError` returns null (`errors.ts:213-215`) and it surfaces as a raw driver error. Separately, the M1
spec welded "tier" to the tiered failure policy (`specs/2026-09-07-m1-stores-design.md:397`) and
`db.ts:147` repeats it, but `trigger_event_tier_needs_harm` (`0006:82`) refuses
a tier on any status but `harm_confirmed`, and a brief records a *candidate*
trigger (design §7:298). The evidence tier (A/B/C) and the intent's risk tier
(low/mid/high) are two different things in one column's mind.

**F6. "Recent permanent records" cannot be read.** Design §6:265 asks for them.
`PermanentRecordRepository` has `promote`, `read(recordId)` and
`get(recordId)` and no listing by namespace; `TriggerEventRepository` has
`record` and `get`. The M1 ledger recorded that the nightly read would want
indexes on the namespace columns of `trigger_event`, `hot_window` and
`permanent_record` (`ledgers/2026-09-06-m1-decisions.md:246`) and none landed.

**F7. The store's public surface cannot construct a `Db`, and the storage card
recorded that finding backwards until one commit before this plan.** `store/src/index.ts` exports no `db.js`, and
every repository constructor takes a `Db`. Measured on the built package:
`dist/index.d.ts` contains none of `openDb`, `withIsoDates`, `Schema`, `Db`. The
entry handed to M3 (`storage-card.md`, the "not fixed" block) said `export *`
carries those names OUT past the header's rule; the opposite shipped. **The
review of this plan found that clause itself stale:** the card was corrected in
`d6b263b`, the commit immediately before this plan, and its entry now reads
"`index.ts` exports LESS than a consumer needs, and the entry that stood here
said the opposite". So the backwards text exists only in `d6b263b~1` and what
the card actually hands M3 is the decision, not the error. Recorded rather than
quietly rewritten, because a plan describing a state that had already been fixed
is the same failure one commit smaller. Two true
facts sat under the false one: `package.json` has no `exports` field, so
`@nonametrust/store/dist/db.js` is deep-importable and the surface is a
convention rather than a boundary; and `retention.ts` is already exported with a
comment at `index.ts:9-12` making exactly this argument one value short of its
conclusion.

**F8. Two scenarios, and they disagree on four numbers.** Design §9:354-362 has
500 units and a `hold`. M2's corpus has one `endpoint` namespace, a 500-unit
quote and a 14-day half-life. M1's story has endpoint plus wallet linked by a
continuity assertion, 2500 USDC, `HALF_LIFE = 7 * DAY` "as tag.test.ts and
strength.test.ts assume", and a hand-chosen g0 of 0.6. And design §8:338-339
says the defaults are "chosen to make the Section 9 scenario behave" — a fitted
number by construction, which is the failure mode this project's own memory
names. M3's acceptance test must not pick numbers to pass.

**F9. "The nightly job is the only writer" is already false.** Design §2:71-74.
`refresh` writes `g0` per decision and the synchronous ingest path writes tags
and baselines. Determinism (design §9:367) has to be claimed over the ingest
path too, not only over the nightly pass.

**F10. The M2 ledger tells M3's engine to check that a state still holds, and
the root gate forbids the read.** M2 ledger 648-660. `gates/single-date-reader.test.ts:45`
scans every `packages/*/src` (applied at `:80-82`) with no exemption for an engine and refuses any
line naming `validUntil`; `datedAt` (`schema/src/timing.ts:8`) returns null for
a state and exposes nothing about its interval. So a state whose validity ended
keeps opening and refreshing tags until either `schema` gains a second reader or
the gate gains an exemption.

**F11. Volatility is assigned to three different milestones.**
`store/src/repositories/volatility.ts:6` says "Mean-reverting in M3"; the M1
spec says M2; the M2 spec says "M3 and M4". The M3 card names none of them, and
the code holds a bare upsert with no arithmetic.

**F12. A candidate trigger needs a finite surprise and a categorical decision
has none.** `trigger_event.surprise` is `not null` and finite (`0006:77`);
`TagDecision.surprise` is null for every categorical reading (`tagging/src/tag.ts:202`).
If the brief builds a candidate trigger from the intent's own reading and the
intent is categorical, there is nothing to store.

**F13. A state's reason has no "original timestamp".** Design §6:272 says each
reason carries one. A state's tag is stamped at `at` and moves every morning,
and its row has `dated_at` null (`0002:39`). The reason shape must admit a
reason with no instant.

**F14. `BaselineRepository.upsert` loses a concurrent fold, silently, and it is
measured.** It is `on conflict do update set` with no predicate — last-writer-wins.
Measured during the survey: two writers each read `count = 10`, each folded one
observation and upserted `count = 11` with a different mean, both statements
succeeded, and the row ended at `count = 11` with one observation's contribution
gone and no error. It is latent today only because nothing outside tests calls
`upsert`; M3's engine is what makes it reachable, on the ordinary path.

## 2. Rulings this plan makes, so no implementer has to

**R1. The brief is a pure function that returns a value AND a list of effects; a
thin wrapper performs them.** Closes F1. It takes its instant, its generated
ids and its policy as inputs — so it calls no clock and no `randomUUID`, and
the same inputs replay to the same output, which is what design §9:367's
determinism claim needs. The effects are a `TriggerToRecord` and an
`AuditBodyToAppend`, in that order, and the audit body names the trigger id
because the core took it as an input rather than the writer discovering it.

**That clause required a store change the first version of this plan did not
name.** `TriggerEventRepository.record` mints its own `randomUUID()`
(`store/src/repositories/trigger-event.ts:57`) and stamps `created_at` from its
own clock (:64); `RecordTriggerEvent` (:25-32) carries no `triggerId`. So as
shipped, the row's id is not the id in the audit body and a retried `record`
writes a second row. Task 2 adds both: `record` takes the id and the instant.
Without that change this ruling is unbuildable, which is what a review measured.

Cost if wrong: three wrappers still share one ordering, which is the point, but
a caller who ignores the effects gets a brief that answered and recorded
nothing. So the wrapper is the supported entry point — and the review's other
point stands: with no `exports` field in `package.json` that split is a
convention and not a boundary, the same shape as F7, and R20 says so.

**R2. The brief's numbers live in a third versioned value, `BriefPolicy`, in
`packages/engine`.** Closes F2. Not added to `Policy`: `Policy` is the tagging
package's and the brief is the engine's, so a brief field there is a number that
package never reads. And the M2 collision map (`ledgers/2026-09-12-m2-decisions.md:517-527`) has
`thresholdBase = surpriseScale = winsorMadMultiple = 3`, so a brief threshold
read off the wrong field would be invisible under a default policy — a separate
value removes that class of bug rather than testing for it. Cost: R7's "the
audit body names both versions" becomes three, and the champion-challenger key
becomes a triple. Recorded as a cost, not hidden.

**R3. "Active" is `strengthAt(tag, at) >= activeFloor`, not "live".** Closes
half of F2. Nothing retires a tag, `listLive` returns every tag ever opened, and
`strengthAt` reaches exactly zero only after about 1074 suppressed half-lives —
so "active = live" means every tag lowers the threshold forever and the threshold
means nothing. `activeFloor` is declared and uncalibrated and says so.

**R4. "Lowers" is multiplicative, not subtractive.** The threshold is an amount
in value units; a subtraction has to name a currency and a factor does not. Two
active tags compose by multiplying. Cost: a factor cannot express "never above
X regardless", which a subtraction can; if that is wanted it is a separate cap
and not this number.

**R5. These three numbers are fitted to the scenario and the plan says so.**
Design §8:338-339 already admits the defaults were chosen to make §9 behave.
This plan does not repeat that as though it were a derivation: §6 below lists
`briefThreshold`, `activeTagFactor`, `relatednessFloor` and `activeFloor` as
declared, uncalibrated, and re-derivable when the shadow evaluation measures a
population.

**R6. The risk tier is an enum on the brief's input, recorded in the audit body
only.** Closes half of F5. Not a column on `trigger_event`:
`trigger_event_tier_needs_harm` refuses a tier on a candidate, and the evidence
tier and the intent's risk tier must not share a column — that conflation is
already written into two documents and one type, and this plan stops it
spreading. Cost: the tiered policy is auditable through the chain and not
queryable by SQL; M4 may want a column and that is M4's migration.

**R7. "Unavailable" is a named set, and `Deadlocked` is NOT in it.** Closes the
rest of F5. The first version of this plan put `Deadlocked` in the unavailable
set, and a review caught that as a quiet reversal of a shipped ruling: 40P01 is
mapped to `Deadlocked` precisely so a caller can tell it from a constraint and
RETRY (`store/src/errors.ts:60-71`, the storage card's R21). Running the tiered
failure policy on it — low proceeds, high holds — throws away the one response
that is correct. So a deadlock is retried under R28's bound, and only an
exhausted retry becomes unavailable.

Unavailable is: a driver error carrying no SQLSTATE, `Cancelled` (55P03/57014),
and a timeout the engine sets itself. And "no SQLSTATE" is not a sufficient
discriminator on its own — a tagging `RangeError` has no code either, and
measured on this cluster a refused connection carries `ECONNREFUSED` while a
connect timeout carries **no `code` field at all** — so the set is matched on the
error arriving from a store call, not on the absence of a field. The condition is written to structured stderr, because the audit chain
lives in the same Postgres that is unavailable, and a reconciliation audit row
is appended when the store returns. The result carries its own code and is not
`hold`, because design §6 says error states are codes and not prose.

**R8. The medium tier's ceiling is an amount on the brief's input.** The engine
reads no amount today: `salienceHints` is read by nothing (M2 ledger 741-743).
So "medium passes under a ceiling" needs the intent's amount and its unit passed
in, declared as part of the brief's input shape rather than inferred.

**R9. `upsert` becomes optimistic and raises `BaselineStale`.** Closes F14. The
predicate is the `n` the caller read; zero rows updated means a follow-up select
distinguishes a stale write from a missing row, exactly as `refresh`
distinguishes `TagRefreshStale` from `TagNotFound`. Chosen over a per-pair
advisory lock because the advisory key space is already shared and unallocated
(the storage card's own "not fixed" list) with a measured deadlock history (R20
there). Cost: the retry loop now has two stale signals, and R10 is what handles
them.

**R10. The fold and the tag write happen in ONE transaction, and the retry
re-runs the whole transaction. This ruling replaced a wrong one, which is why it
carries its measurement.**

The first version of this plan ruled "baseline first, then tag, and the retry
re-reads both". A review measured it and it is wrong in the direction that
matters: baseline-first does not avoid the double fold, it CREATES a committed
fold with no tag, and the prescribed retry then folds the observation a second
time — because `tagReading` always computes `next = updateBaseline(before,
value)` and the re-read baseline already contains the first fold. R9 cannot catch
that, because the expected `n` was re-read after the fold landed. **Measured with
the real repositories: one writer retried once left `count = 12` for 11
observations, with the mean moved.** And the mutant G12 named — "the retry
re-reads only the tag" — was the wrong mutant, because re-reading both
double-folds as well.

Skipping the re-fold on a retry is no better: it judges the surprise against a
baseline that already contains the reading, which violates tagging's own fixed
order — judge against the baseline as it stands BEFORE the reading joins it
(`tagging/src/tag.ts:328-330`).

So the unit of work is a transaction. Both writes are single statements and both
compose on a `Transaction` under R21 — only `append`, `AuditChain.append` and
`promote` refuse one — and one write order per pair cannot cycle. A stale tag or
a stale baseline rolls the whole thing back and the retry re-reads and re-decides
from a state that contains neither write. **Measured: the stale case rolls back
with the count unchanged and the retry lands +1; twenty concurrent writers on one
pair in the same order landed 20 of 20 with 179 stale retries and zero
deadlocks.**

What this costs, said plainly: the intent's `append` and the audit row stay
OUTSIDE that transaction, because both refuse one. So `observe` is a transaction
with two writes around it, and R24 rules what happens when the transaction
commits and the audit row does not.

**R11. Cross-namespace relatedness is NOT in M3, because the wire cannot express
it. This ruling reverses the first version of this plan and the reversal is the
finding.**

The first version ruled a `namespace_link` table written at ingest from an
observation's continuity assertion. A review read the schema:
`continuityAssertionSchema` is `{assertedBy, assertedAt, reason}`
(`schema/src/namespace.ts:13-19`) — **there is no target namespace in it.** M1's
own story names the endpoint only inside the free-text `reason` ("the payment
address https://data.example/x402 advertises",
`store/src/acceptance.test.ts:135-139`). So `to_namespace_id` is derivable from
no wire observation, and a table for it would be populated by nothing but a test.
The indexer contract says so too: continuity need not be written in v0
(`docs/observation-contract.md:298`).

Two further reasons the first version was wrong to move it: the assertion is
stored as provenance INSIDE the sealed envelope by M1's design, pinned round-
tripping through the payload (`store/src/acceptance.test.ts:284`), so lifting it
into a clear column reverses that without naming it; and the disclosure is bigger
than "a graph", because `reason` and `asserted_by` are integrator free text and
the example reason carries the endpoint URL verbatim.

So: M3's relatedness is WITHIN one namespace. The link is M4's, and it needs a
schema change first — a target namespace on the continuity assertion, in
`@nonametrust/schema` and in the indexer contract, which is a versioned wire
change and not a migration. Written here so M4 inherits the reason rather than
the conclusion.

**R12. Relatedness is `sameNamespace × channelAffinity`, and the
same-namespace-different-channel term is NOT zero.** Closes F4 for M3's scope,
and closes a contradiction two reviewers found independently: the first version
made relatedness a product with a channel-agreement term, and the acceptance
scenario's own case is same namespace, DIFFERENT channel — the day-twelve tag is
`address_integrity/transition` and the day-twenty-one intent is `price`. Under a
zero agreement term the address change scores zero, is therefore not a reason,
and design §9:359-361 and Task 9 both require it to be one. The plan would have
been discovered self-contradictory on the last task, and closed on the day by an
invented constant — the fitted number R5 exists to forbid.

So the terms are named: same namespace and same `(channel, aspect)` is 1; same
namespace, different channel is `crossChannelAffinity`, a fifth `BriefPolicy`
field, **declared uncalibrated**; different namespace is 0 in M3 by R11. Design
§1's out-of-scope table already implies the middle term must be non-zero: "entity
graph and aspect matching carry v0 behind the same `rel()` interface".

**R13. A reason whose evidence is unreadable is KEPT, with a code — and it needs
a store read that does not exist yet.** Closes F3.
`SOURCE_UNREADABLE`, carrying the columns that survive in the clear:
`dated_at`, `channel`, `aspect`, `evidence_kind`. Omitting the reason would make
the brief's answer change as retention runs — the output would depend on the
calendar rather than on the evidence, which is the worst of the three options.
Refusing the brief is worse still. **And this is an outward claim:** the brief
can cite a reason whose opening observation was ingested 90 to 120 days ago
without its source, and that sentence belongs in the README and the whitepaper
rather than being discovered by a user.

Two things a review added. **The read does not exist:** every public path to an
observation decrypts (`get` → `read`, `observation.ts:464`) and the
non-decrypting `skeleton` is private and keyed on the idempotency key, so Task 2
adds a public read by observation id that returns the clear columns and no
payload. And **this reverses the M1 ledger's own principle** (:118-121, "evidence
whose content is permanently unreadable can only produce a reason nobody can
explain") — which was the stated reason to refuse a promotion into a shredded
namespace. R13 emits exactly such a reason, on purpose, because the alternative
makes the answer depend on the calendar; the reversal is named here rather than
left for someone to find.

**R14. `listLive` gains a shred gate at the engine, not in the store.** An
erased namespace's tags come back today and every source read raises
`NamespaceShredded`. The store's `listLive` keeps answering, because a caller
asking "what tags exist" is entitled to the skeleton; the engine refuses to
brief on an erased namespace by name, before it reads a tag.

**R15. The acceptance scenario is M1's story, with the CALIBRATED half-life and
M2's prior quotes merged in, because M1's story alone is arithmetically COLD.**
Closes F8. Endpoint plus wallet linked by a continuity assertion, 2500 USDC, and
14 days — not 7. 14 days is the product's number; the store's own
acceptance test keeps 7 for its own reasons and the plan records why the two
differ instead of unifying them.

**Two claims the first version made and a review refuted.** It said the wallet
link is what makes relatedness non-trivial — false of this scenario: both the
address change and the quote are on the PROVIDER, the wallet holds one routine
payment and no tag, and under R11 the link is out of M3 entirely. And it did not
notice that the story is cold: `POLICY_V0.minObservations` is 10 and M1's story
gives the provider ONE price observation, so `judgeSurprise` returns cold,
nothing crosses on day twenty-one, and `trigger_event.surprise` is NOT NULL — the
brief would have had no candidate trigger to note. So the scenario merges M2's
corpus and its twenty prior quotes. The count is not chosen: the test computes
the bound from `minObservations` rather than hard-coding it, which is the shape
the producer cap's own test uses.

**R16. The state-validity check is `holdsAt(observation, at)` in
`schema/src/timing.ts`, and the root gate gains NO exemption.** Closes F10. The
first version ruled the opposite — the check in the engine with a named gate
exemption — and a review showed the rejected alternative is better by the gate's
own design: `schema/src/timing.ts` is already the one exempt date reader
(`gates/single-date-reader.test.ts:31-39`) and holds no interval today, so
putting `holdsAt` beside `datedAt` is not "the interval in two places", it is
the designated place. Exempting a file in the one package that imports both store
and tagging would also have forced a change to the gate's own sentence, "a new
package enters under it on the day it is created, with no exemption" (:16-17).
Cost: `@nonametrust/schema` gains a function, so its version moves.

**R17. Volatility and the hot window are M4's, and this plan says so once.**
Closes F11. Three documents disagree; the brief reads no volatility, and the
nightly job is what would maintain it. M3 touches neither.

**R18. A categorical intent builds no candidate trigger.** Closes F12. The
trigger's `surprise` is not null and a categorical reading has none, so the
brief returns its grade with no trigger effect rather than inventing a number.
Cost: a categorical intent is not counted in the trigger table; M4's
consolidation reads tags, not triggers, so nothing downstream breaks.

**R19. The reason shape admits a reason with no instant.** Closes F13. A state's
reason carries `datedAt: null` and says so in its code rather than borrowing the
tag's moving `tagged_at`.

**R20. `index.ts` exports `openDb` and the `Db` type, and its header sentence
changes.** Closes F7. Measured: the surface as declared cannot construct a
repository. Deep-importing `dist/db.js` would make the boundary a fiction, and
`retention.ts` was already exported on exactly this argument. The sentence
becomes "repositories, errors and the connection are exported; the SQL is not".

**R21. A per-observation refusal is recorded as a code and an observation id,
never as the message.** `surpriseOf`'s `RangeError` carries the observed value
(`tagging/src/scale.ts:63`), and an audit body outlives both the month key and
the namespace key (F7 of the storage card: the chain hashes the caller's body
and no ciphertext digest). So the code goes in and the message does not.

**R22. `brief` does not ingest, and the intent's OWN tag is excluded from its own
threshold.** The caller runs `observe(intent)` and passes the returned
observation id to `brief` — so `observe` gains a return shape that carries the id,
which nothing specified before. And the brief filters out any tag whose
`observation_id` is the intent's, because in the shipped corpus the day-twenty-one
quote OPENS a price tag the moment it is observed
(`tagging/src/acceptance.test.ts:481`, `"21:price:new"`): without the filter the
intent's own deviation is both a reason and an "active tag" lowering the very
threshold it is judged against, and §9's `hold` would pass for the wrong reason
while the day-twelve reason sat there decoratively. Two reviewers found this
independently; neither the design nor the first version of this plan rules it.

**R23. `observe` on a re-delivery folds nothing, and says so in its return.**
`append` answers `{created: false, readable: true}` on a repeat — the indexer's
normal retry path. Nothing records which observations a baseline has absorbed
(`baseline` holds `n` and the moments only), so a re-delivery cannot tell whether
the first fold landed. Folding again double-counts, which is the duplicated-trace
defect the design names at §3:189-191. So a re-delivery returns
`{ created: false, folded: false }` and the cost is stated rather than hidden:
**a crash between a successful `append` and its fold loses that observation's
contribution permanently, and nothing detects it.** Closing that properly needs a
fold ledger, which is a migration and a table, and it is M4's — recorded here so
M4 inherits the reason.

**R24. The audit row is written after the transaction commits, and a missing one
is a named inconsistency rather than a rollback.** `AuditChain.append` refuses a
`Transaction`, so it cannot join R10's unit of work. If the transaction commits
and the audit row does not, the engine has a fold and a tag with no chain entry.
The engine retries the append under R28 and, if that is exhausted, writes the
condition to structured stderr with the ids — it does NOT roll back a committed
fold to keep the chain tidy, because the chain's job is to record what happened
and not to be the transaction log.

**R25. The brief's audit body carries ids, codes, versions and instants, and
never a source reference or a payload field.** This is the storage card's F7
decision, which the card explicitly hands M3 and the first version of this plan
cited without making. The chain hashes the caller's body and no ciphertext
digest, and an audit row outlives BOTH the month key and the namespace key — so a
wrapper that logged the brief's reasons with their sources would defeat erasure
through the audit table. A gate plants a `payload` and a `source` key in a body
and goes red.

**R26. `audit_entry.policy_version` holds the composite, and the format is fixed
here.** One column, four versions now (retention, tagging policy, calibration,
brief policy), joined as `retention/tagging/calibration/brief` with each
component's own version string and no separator any of them may contain. R2 said
"three" and `retention.ts:45` says the retention version must appear too, so it
is four.

**R27. `briefThreshold` and the medium tier's ceiling are both amounts in ONE
declared unit, and an intent whose unit differs is refused by name.** R8 put the
ceiling on the input, and a review pointed out that a caller supplying its own
ceiling bypasses design §6:281's "degrading availability is not a way to bypass
the layer". So the ceiling is a `BriefPolicy` field, not an input; the intent
carries an amount and a unit; and a mismatch is a named refusal rather than a
coercion. `BriefPolicy` therefore has seven fields, not four:
`briefThreshold`, `thresholdUnit`, `activeTagFactor`, `activeFloor`,
`relatednessFloor`, `crossChannelAffinity`, `mediumCeiling`.

**R28. Every retry is bounded by `maxRetries`, declared in `BriefPolicy`, and an
exhausted retry is recorded.** `BaselineStale`, `TagRefreshStale`, the 23505 on
`tag_one_live_per_pair`, and now `Deadlocked` under R7 all retry. An unbounded
retry loop is a denial of service on ourselves, which is the argument the producer
cap already makes. An exhausted retry records its code and the observation id and
returns, and the observation is not folded.

**R29. A COLD continuous intent builds no candidate trigger either.** R18 ruled
that for a categorical intent; a review found the other half. `judgeSurprise`
returns cold when the baseline holds fewer than `minObservations`, so it computes
no surprise — and that is the COMMONEST brief, a counterparty seen for the first
time. The brief returns its grade with no trigger effect, and the grade rests on
the threshold and the relatedness of whatever tags exist, which for a new
counterparty is none. So a first-ever brief grades `clear` on no evidence, and
that sentence belongs in the README: the absence of a reason is not a reassurance.

**R30. A refreshed tag's reason cites the tag's OPENING observation, and says
so.** F3 noted that a tag refreshed forty times records the other thirty-nine
nowhere. "Sources" is plural in the design and singular in the data, and M3 does
not change the schema to fix it: the reason carries the opening observation and a
`refreshCount`, so a reader can see that more evidence exists without the plan
pretending it can name it. Recording the rest is a column and therefore M4's.

**R31. `trigger_event` has no guard, and M3 does not add one.** `0006` has no
trigger on it, so the candidate the brief records — its only durable trace beside
the audit row — is updatable and deletable from any raw writer, unlike every other
table in this schema. Out of M3's scope because the brief only writes it and the
guard belongs with the milestone that reads it, but stated rather than left as a
surprise: it is the first table the synchronous path writes and it is the one
table with no protection.

**R32. `AppendResult`'s identity typing is fixed in `schema`, not worked around in
the engine.** The storage card's own unfixed list hands this to M3: the
unreadable arm declares `observationId: string` while the readable arms carry an
`Observation` whose `observationId` is optional, so a caller narrowing on
`created` gets a different type for the same field, and `storedObservation` in the
store's test harness exists to paper over it. The engine is the first real
consumer, so `schema` gains a stored-observation type with the id required and the
harness helper stops being the only narrowing.

## 2b. What the review of this plan changed, and why the record matters

Three reviewers read the first version in isolated worktrees and databases, one
per lens: are the findings true, are the rulings sound, what is missing. They
converged independently on two things, which is the strongest signal a review
gives.

**Measured, and the plan was wrong.** R10 ruled "baseline first, then tag, and
the retry re-reads both". Running it with the real repositories left `count = 12`
for eleven observations and moved the mean: baseline-first does not avoid the
double fold, it creates a committed fold with no tag, and the prescribed retry
folds again because `tagReading` always folds the reading into whatever baseline
it read. The alternative the plan never weighed — both writes in one transaction —
measured 20 of 20 writers landing on one pair with 179 stale retries and zero
deadlocks. **A ruling that had an argument and no measurement lost to one that had
both.**

**Unbuildable as written, three of them.** R1's audit body could not name the
trigger id because `record` mints its own; R11's link table had no target to
write, because `continuityAssertionSchema` carries `{assertedBy, assertedAt,
reason}` and no target namespace at all, so the endpoint appears only inside free
text; R13's kept reason had no non-decrypting read to build it from. Each is now
either a store change named in Task 2 or, for R11, a scope exclusion with the
schema change it would need written down for M4.

**A quiet reversal of a shipped ruling.** R7 put `Deadlocked` in the unavailable
set. 40P01 was mapped to `Deadlocked` on the storage card precisely so a caller
can tell it from a constraint and RETRY; running the tiered failure policy on it
throws away the one correct response. The plan reversed a ruling it had read,
without noticing. R7 now retries it and G15 plants the reversal.

**Two self-contradictions, found from opposite directions.** R12's relatedness
product scored the acceptance scenario's own case at zero — the day-twelve tag is
`address_integrity` and the intent is `price` — so the address change would not
have been a reason while §9 and Task 9 both require it. And R15's scenario is
arithmetically cold: `minObservations` is 10 and M1's story gives the provider one
price observation, so nothing crosses on day twenty-one and there is no surprise
for a candidate trigger. Either would have surfaced on the last task and been
closed with an invented constant.

**Eleven decisions the plan did not rule at all**, now R22-R32. The two that
matter most were invisible from inside: the intent's own tag lowers the very
threshold it is judged against, because the day-twenty-one quote opens a price tag
the moment it is observed; and a re-delivered observation has no way to know
whether its fold landed, because nothing records which observations a baseline has
absorbed.

**And one thing the plan predicted about itself and then did not fix.** Its risks
section said "the engine needs its own gate entry" for the clock, and no task
delivered it — a rule stated in prose and held by nothing, which is §3b's own
prohibition, in the document that contains §3b. Task 1 now delivers it, and G10's
replay test advances the clock between runs because a frozen one would have let
the plant through.

**Nine ungated rulings became five.** The ten that remain are listed under §5
with the reason each cannot have a gate.

The findings held better than the rulings: twelve of fourteen stood exactly as
written. F3 overstated its interval — the grace runs from the close of the
ingestion month, so the window is 90 to 120 days after ingest and not "roughly
four months", and the half-life does not enter the arithmetic at all. F7's clause
about the storage card described a state the card had corrected one commit
earlier. Four citations pointed at the wrong line with the substance intact. The
one finding that was only read rather than measured is the one that was wrong,
which is the lesson: **a number in a finding is a claim, and a claim gets
measured.**

## 3. Global constraints for every task

- **The engine is the only module that may import both packages.** A root gate
  holds it: nothing in `packages/store/src` imports tagging, nothing in
  `packages/tagging/src` imports store, and only `packages/engine/src` imports
  both.
- **The engine computes nothing a decision depends on.** It composes. `g0`,
  `taggedAt`, the saturation state and the surprise all come from M2 and are
  passed to the store as handed — which is the storage card's corrected version
  of "the store computes nothing".
  **CORRECTED BY R44, and the words rather than the meaning.** The engine now
  computes the threshold — `applied = base × factor^k` — and the grade, because R44
  moved both into Task 5. What the sentence means is still true and is what matters:
  every INPUT to a decision comes from M2 or the store and none is invented here.
  Marked rather than rewritten, because the sentence is cited elsewhere.
- **`at` is the engine's clock on every path, including replay**, and it is the
  same `Clock` object the store holds: `open` and `refresh` refuse a `taggedAt`
  after `clock.now()` (R12 of M2), and the store's own constructor now refuses a
  clock that is not its namespace repository's.
  **TWO CORRECTIONS, both measured.** "Including replay" is false and R1 requires it
  to be: `at` is an INPUT to the core on the replay path, which is what makes replay
  possible at all. Task 5 resolves this by making the replay entry point the core,
  which holds a read-only port and cannot write, while the only thing that writes
  takes its instant from the object that writes (R58). And "the store's own
  constructor now refuses a clock that is not its namespace repository's" is true of
  exactly ONE pair — `ObservationRepository` against its `NamespaceRepository` — and
  false of the other seven clock-bearing classes, which take it unchecked. That is
  why `compose` and its gate exist.
- **Every refusal names its field or its class.** A brief that fails must say
  which store, which tier and which code.
- **Assert a refusal's message or constraint name, not only its class** — the
  M2 ledger's test habit, which caught four rules on the storage card.
- **Override every `BriefPolicy` field in at least one test with a number no
  other field shares.** The M2 collision map is why: three of its fields were 3.
- **For every test in a brief, delete the line it claims to protect and confirm
  the test fails.** Report any that stay green.

## 3b. The mutation step is not optional

After a task is green: remove each rule one at a time and RECORD which test goes
red. A surviving mutant is an unheld rule. Three lessons this repository paid
for, in order of how much they cost:

1. **When a mutant dies, ask WHICH test killed it.** A test of another rule
   going red is not evidence. This was got wrong once and written into a commit
   message as "measured".
2. **Mutate both sides of a binding consistently as well as separately.** A
   consistent rename passes every round-trip test.
3. **Colliding fixture values make a rule invisible.** Four times on the storage
   card, once because `shredded_at` and `expires_at` were the same instant in the
   only test that asserted either.

And re-run the mutants this plan's own earlier tasks claim, at the end. On the
storage card, 145 re-run mutants found four killers that had stopped killing —
one disarmed by a later task adding a second call a stub did not cover.

## 8. Risks: where a plausible implementation is silently wrong

- **A retry that re-reads the tag and not the baseline.** Folds the same
  observation twice, and the count is the only witness. G12.
- **A brief that reads the threshold it just lowered.** The threshold query and
  the brief must read one value at one instant; two reads at two instants make
  the answer depend on how long the brief took.
- **`activeFloor` as a float comparison at exactly the floor.** The storage
  card lost four rules to fixture values that coincided; here the floor and the
  decayed strength will coincide unless the test chooses them not to.
- **A reason omitted rather than coded when its source is unreadable.** The
  brief's answer then changes as retention runs and nothing fails.
- **The engine's clock and the store's clock being two objects.** The store now
  refuses that between two of its own repositories; the engine must pass the
  same object down or it will be refused at construction — which is the good
  case. The bad case is passing `new Date()` somewhere, which the clock gate
  catches only inside `packages/store/src`; the engine needs its own gate entry.
- **`namespace_link` treated as inference.** A link is an assertion. The moment
  the engine writes one it did not read from a payload, the identity model's
  central sentence — an address is an attribute of a counterparty, and the two
  are linked by an assertion and never inferred — stops being true.
